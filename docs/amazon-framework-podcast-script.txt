Welcome to QA Unpacked. This episode is a guided tour of the Amazon India Playwright TypeScript automation we built for the TV search assessment. I am going to walk through every file, every class, and every important setting, in the same order a new engineer would open the repo.

Let’s start with the assignment, because the framework only exists to satisfy that story. The test must open Amazon.in, search for television, apply a fifty-five inch filter from the left sidebar, pick two TV brands, open the first product in the filtered list, capture title, price, and product details, and write all of that into a log file. Playwright drives a real Chromium browser. TypeScript gives us types so locators, pages, and captured data stay consistent.

Open the project root. You will see package.json, tsconfig.json, playwright.config.ts, a tests folder, a pages folder, a utils folder, logs, and a README. That split is intentional. Configuration lives at the root. User actions live in page objects. The scenario lives in the spec. File writing lives in a helper. The log is an output, not part of the test logic.

Episode one, package.json. This file names the project amazon-in-playwright-assessment and declares three development dependencies. At Playwright Test is the test runner, the browser automation API, and the expect assertions. TypeScript is the compiler. Types for Node lets us import file system and path without TypeScript errors. The npm scripts are shortcuts. npm test runs playwright test. npm run test colon headed opens a visible browser. npm run test colon ui opens Playwright’s interactive UI. npm run report opens the HTML report after a run. Nothing in this file talks to Amazon. It only describes how Node installs and starts the framework.

Episode two, tsconfig.json. This tells TypeScript to compile to modern JavaScript, use CommonJS modules, turn on strict type checking, and include tests, pages, utils, and the Playwright config. Strict mode matters here because locators return Locator, page methods return Promise void, and ProductInfo is a typed object. If you mistype a field name, the compiler stops you before the browser even opens.

Episode three, playwright.config.ts. This is the control room. testDir points at the tests folder. fullyParallel is false and workers is one, so we run one Amazon session at a time. Amazon search pages are heavy and share cookies in a confusing way if two tests hit them together. forbidOnly fails the suite in CI if someone left test.only in the file. retries is one in CI and zero locally, so a flake can retry in automation but you see the real failure on your machine. timeout is one hundred twenty seconds because search, filters, product load, and accordion expansion take time. expect timeout is fifteen seconds so assertions wait for the UI instead of failing on the first missing node. reporters are list in the terminal and HTML saved to disk with open never, so the run does not pop a browser report automatically. Under use, baseURL is https://www.amazon.in, so page.goto slash means the Amazon home page. locale is English India and timezone is Asia Kolkata, which matches rupee prices and delivery copy. viewport is fourteen forty by nine hundred, wide enough for the left filter rail. screenshot, video, and trace are retained only on failure so a broken run is diagnosable. actionTimeout is twenty seconds and navigationTimeout is forty five. The only project is Chromium using Playwright’s Desktop Chrome device profile, because this assessment is Chrome only.

Episode four, the Page Object Model. We do not put Amazon selectors in the spec. HomePage, SearchResultsPage, and ProductPage each own their locators and speak in user language: open, search, apply filters, capture product info. If Amazon changes a checkbox, you fix one class, not a long recorded script.

Episode five, HomePage. The constructor stores the Playwright page and two locators. Search box is hash twotabsearchtextbox, Amazon’s global search field. Search submit is hash nav-search-submit-button. The open method goes to slash using baseURL, waits only until DOM content is loaded, then dismisses interstitials. dismissInterstitials is defensive. Amazon sometimes shows Continue Shopping, a cookie bar, or a location modal. Each overlay is clicked only if it is visible, with a short timeout, and failures are swallowed so a clean session is not blocked by a popup that never appeared. search waits until the search box is visible, fills the term Television, clicks submit, and waits for DOM content loaded. That is the whole home page contract: get onto Amazon, get past gates, run a search.

Episode six, SearchResultsPage. refinements is hash s-refinements, the left filter column. resultCards is every node with data-component-type s-search-result. waitForResults waits until the first card is visible, up to thirty seconds. applyDisplaySizeFiftyFiveInch waits for the filter rail, then tries three locators in order. First, the Popular Shopping Idea whose accessible name is fifty-five followed by an inch mark, including the Unicode double prime Amazon actually uses. Second, the screen size range Apply the filter fifty-three point zero to sixty-one point nine in, which is the bucket that contains a fifty-five inch TV. Third, any link whose name looks like fifty-five inches. After the click it waits for the document and for result cards again. applyBrands takes preferred brands Sony and Samsung. It expands the Brands list, including See more. It clicks a preferred brand if the Apply the filter link is visible. If Sony disappears after the size filter, which happens on Amazon.in, it fills the remaining slots from whatever brands are still listed, for example Samsung and LG. If it cannot get two brands, it throws. brandFilterLink builds a regular expression around Apply the filter plus the brand name. escapeRegExp is a tiny helper so a brand with special characters cannot break that regex. openFirstProduct finds the first result card that has an h two heading and an anchor whose href contains slash d p slash, Amazon’s product URL pattern. It starts waiting for a popup in case the product opens in a new tab, clicks, and returns either the popup or the same page. That return value is a Playwright Page, which ProductPage will wrap.

Episode seven, ProductPage. ProductInfo is the typed payload: title, price, productDetails, extras, url, and capturedAt. The title locator is span hash productTitle, not hash productTitle alone, because Amazon also puts a hidden input with the same id and Playwright strict mode would fail on two matches. feature bullets is hash feature-bullets, the About this item list. waitForLoaded waits for the visible title. captureProductInfo reads title, price, about this item, expanded product details, then extras: brand from byline, availability, rating, and ASIN. capturePrice tries several Amazon price selectors, preferring the offscreen a-price text which usually holds the rupee amount accessibly. captureProductDetails scrolls to hash prodDetails, the Product information accordion. captureExpandedDetailSections finds every a-expander-section-header, skips headings that match Feedback or tell us about a lower price, clicks headers that are not already expanded, waits for table prodDetTable, and writes each row as label colon value under a section heading in square brackets. If a table is missing it falls back to the expander content text, still stripping excluded lines. If the accordion is absent it tries older tech spec tables, then About this item. readAsin looks in detail bullets, then parses a ten character ASIN from the URL.

Episode eight, productLogger. writeProductLog takes ProductInfo, creates a logs directory if needed, and writes product-details.log. The file has a header with timestamp and URL, a mandatory block for title, price, and the expanded details, then additional information for about this item, brand, availability, rating, and ASIN. The test does not print secrets. It writes a plain text artifact you can attach to an assessment.

Episode nine, the spec, amazon-tv-search.spec.ts. It imports test and expect from Playwright Test, the three page objects, and writeProductLog. SEARCH_TERM is Television. BRANDS is Sony and Samsung. test.describe groups the scenario. One test receives a page fixture, Playwright’s already-launched browser tab. It constructs HomePage and SearchResultsPage. Each test.step is a named chapter in the trace. Step one opens Amazon and asserts the URL matches amazon dot in. Step two searches and waits for results. Step three applies the fifty-five inch filter. Step four applies two brands and asserts the array length is two. Step five opens the first product and may return a new tab. Step six wraps that page in ProductPage, captures info, asserts title, price, and details are non-empty, writes the log, and asserts the path contains product-details.log. The spec reads like the assignment. The how lives in the pages.

Episode ten, how a run actually works. When you type npm test, Playwright reads the config, launches Chromium, injects the page fixture, and executes the describe block. Headless means no window. npm run test colon headed, or playwright test with the headed flag, shows Chromium so you can watch search, filters, the product page, and each accordion open. On failure you get a screenshot, a video, and a trace zip you can open with playwright show-trace. On success you get a green list reporter line and a refreshed log file.

That is the whole framework, from npm metadata to the last expander row. Playwright is the engine. TypeScript is the contract. Config is the environment. Page objects are the user. The spec is the story. The logger is the evidence. Thanks for listening to QA Unpacked.
